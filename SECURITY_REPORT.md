# Security Inspection & Audit Report: Brain Builder

This report presents a security audit of the **Brain Builder** cognitive architecture platform. As an interactive application designed to build neural frameworks and cognitive models, the platform integrates with Firebase services (Firestore, Auth) and the Google Gemini AI API via Cloud Run.

This report evaluates **10 key security vectors**:

1. **XSS (Cross-Site Scripting)**
2. **SQL Injection**
3. **NoSQL Injection**
4. **CSRF (Cross-Site Request Forgery)**
5. **Authentication Weaknesses**
6. **Authorization Bypass**
7. **Exposed Secrets**
8. **Unsafe Storage**
9. **Token Leaks**
10. **Insecure API Endpoints**

All recommendations provided in this report are **minimal and non-intrusive**, ensuring full preservation of application logic and existing functionality (including collaborative user profile access).

---

## Executive Summary

The application architecture relies on Firebase client SDKs, Firestore security rules, and server-side Gemini API calls via Cloud Run. The overall security posture is resilient against standard database injection attacks (such as SQL injection) due to serverless Firestore parameterization. However, specific vectors around client-side token handling, content sanitization, CSRF on custom API endpoints, and Firestore rule constraints warrant targeted, non-intrusive hardening.

---

## Detailed Security Vector Evaluations

### 1. Cross-Site Scripting (XSS)
- **Risk Level:** Medium
- **Vector Assessment:**
  - Neural architecture nodes, prompt outputs, and cognitive model data generated by users or the Gemini AI model are dynamically rendered on canvas displays and UI panels (e.g., using D3 or Recharts).
  - If dynamic text from AI responses or imported JSON architectures is rendered using raw HTML setters (`dangerouslySetInnerHTML` or direct DOM innerHTML mutation) without sanitization, malicious script payloads could execute in the user's browser context.
- **System Impact:** Potential session token theft or unauthorized client-side actions if arbitrary JavaScript executes.
- **Minimal Non-Intrusive Security Fixes:**
  - Rely on React's default JSX string escaping for standard UI text elements.
  - If dynamic HTML or SVG attributes must be parsed from user/AI inputs, sanitize payloads using a lightweight DOM sanitization library (e.g., `DOMPurify`) prior to insertion.
  - Implement a basic Content Security Policy (`CSP`) header in response headers restricting script sources to trusted origins.

### 2. SQL Injection
- **Risk Level:** Low / Not Applicable
- **Vector Assessment:**
  - The application relies entirely on Firebase Firestore (a NoSQL document store) and client/server REST APIs; no relational SQL databases or raw SQL queries are utilized.
- **System Impact:** None under current architecture.
- **Minimal Non-Intrusive Security Fixes:**
  - Preserve parameterization and ORM abstractions if any SQL-backed microservices are introduced in future developments.

### 3. NoSQL Injection
- **Risk Level:** Low
- **Vector Assessment:**
  - Firestore access is routed through the official Firebase Web SDK, which uses strongly typed method parameters (`doc()`, `collection()`, `where()`) that automatically escape and parameterize input.
  - Unstructured operator injection (e.g., MongoDB-style `$gt` parameter pollution) is inherently prevented by the Firestore SDK client architecture.
- **System Impact:** Low risk of query logic manipulation or unauthorized data retrieval through query operator manipulation.
- **Minimal Non-Intrusive Security Fixes:**
  - Validate and sanitize input string types (e.g., checking that `userId` strings match expected alphanumeric formats) before passing them as path parameters or query filters.

### 4. Cross-Site Request Forgery (CSRF)
- **Risk Level:** Medium
- **Vector Assessment:**
  - Primary authentication uses Firebase Auth Bearer tokens (`Authorization: Bearer <token>`) passed explicitly in request headers rather than ambient, browser-managed session cookies.
  - However, custom serverless endpoints or Cloud Run handlers that process CORS requests could be susceptible if origin headers are unvalidated.
- **System Impact:** Potential unauthorized state modification if cross-origin requests are accepted blindly without header checking.
- **Minimal Non-Intrusive Security Fixes:**
  - Ensure all API endpoints enforce strict CORS policies allowing only trusted origins (matching `APP_URL`).
  - Validate `Origin` and `Referer` headers on write endpoints, and require explicit Authorization Bearer headers for state-changing endpoints.

### 5. Authentication Weaknesses
- **Risk Level:** Medium
- **Vector Assessment:**
  - Authentication lifecycle is managed by Firebase Auth, including token generation, signing, and automatic hourly refreshes.
  - Weaknesses can arise if unauthenticated states fail to gracefully redirect users or if token expiration events drop uncommitted work without notification.
- **System Impact:** User confusion or unexpected permission errors when attempting operations with expired credentials.
- **Minimal Non-Intrusive Security Fixes:**
  - Implement an `onIdTokenChanged` auth state listener to seamlessly detect token expirations and request credential refresh before initiating network writes.
  - Provide user-friendly authentication error messaging for sign-in failures without exposing sensitive system internals.

### 6. Authorization Bypass
- **Risk Level:** Low / Medium
- **Vector Assessment:**
  - Firestore security rules in `firestore.rules` define explicit match paths:
    ```rules
    match /users/{userId} {
      allow read: if request.auth != null;
      allow write: if request.auth != null && request.auth.uid == userId;
    }
    match /personality_tests/{userId} {
      allow read, write: if request.auth != null && request.auth.uid == userId;
    }
    ```
  - `/users/{userId}` allows read access to any authenticated user (`request.auth != null`), preserving collaborative features (such as searching/loading collaborator profile information).
  - Write permissions for both `/users/{userId}` and `/personality_tests/{userId}` strictly enforce ownership (`request.auth.uid == userId`).
- **System Impact:** Unauthorized modification of other users' data is blocked by security rules. Profile enumeration is limited to authenticated users to support collaboration.
- **Minimal Non-Intrusive Security Fixes:**
  - Preserve the permissive `/users/{userId}` read rule to maintain collaborative functionality while ensuring write rules strictly validate `request.auth.uid == userId`.
  - Add non-intrusive schema validation rules (e.g., enforcing data types and immutable field checks) inside `firestore.rules` without altering existing read/write logic.

### 7. Exposed Secrets
- **Risk Level:** Low
- **Vector Assessment:**
  - Secret keys like `GEMINI_API_KEY` are documented in `.env.example` as being injected dynamically at runtime by AI Studio environment configuration.
  - `.gitignore` properly excludes `.env*.local` files from source control.
  - Public Firebase client configurations in `firebase-applet-config.json` contain public identifiers (`apiKey`, `projectId`, `appId`), which are expected to be public in Firebase architecture.
- **System Impact:** Minimal risk of secret leaks if environment injection rules are maintained.
- **Minimal Non-Intrusive Security Fixes:**
  - Ensure backend Gemini API calls route through serverless Cloud Run functions so `GEMINI_API_KEY` is never exposed in client-side bundles.
  - Verify that local developer secret files (`.env.local`) remain explicitly listed in `.gitignore`.

### 8. Unsafe Storage
- **Risk Level:** Medium
- **Vector Assessment:**
  - Local client storage (`localStorage` or `sessionStorage`) used for caching cognitive architectures or application settings could leak data if persistent sensitive tokens are stored in plain text.
- **System Impact:** Potential credential or PII leakage if client machine access is compromised or XSS occurs.
- **Minimal Non-Intrusive Security Fixes:**
  - Rely on Firebase Auth SDK's default in-memory or `IndexedDB` secure session management instead of writing raw ID tokens or refresh tokens into `localStorage`.
  - Clear temporary cached session data upon explicit user logout.

### 9. Token Leaks
- **Risk Level:** Low / Medium
- **Vector Assessment:**
  - Firebase ID tokens or API keys could inadvertently leak through HTTP `Referrer` headers, URL query strings, or client-side console logging during debugging.
- **System Impact:** Intercepted tokens could enable temporary unauthorized API access until token expiration.
- **Minimal Non-Intrusive Security Fixes:**
  - Set the HTTP `Referrer-Policy` header to `strict-origin-when-cross-origin` on application responses.
  - Ensure authentication tokens are passed exclusively in HTTP request `Authorization` headers and never as URL query parameters.

### 10. Insecure API Endpoints
- **Risk Level:** Medium
- **Vector Assessment:**
  - Serverless API endpoints or Cloud Run services handling Gemini requests must verify incoming request authenticity and validate payload schemas.
- **System Impact:** Unprotected endpoints could be abused for unauthorized AI token usage or server resource exhaustion.
- **Minimal Non-Intrusive Security Fixes:**
  - Verify Firebase ID tokens on the server for all protected routes using `admin.auth().verifyIdToken(token)`.
  - Enforce payload size limits (e.g., max 2MB) and validate input structures on API endpoints to prevent excessive AI billing or service overload.
